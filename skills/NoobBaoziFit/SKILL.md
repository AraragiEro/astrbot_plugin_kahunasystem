# EVE 配船知识库使用指南

## 第一原则：先查库，后调工具

**这个库已经存了 28 个船型的完整分析。凡是库里有的，直接引用，不要重算。**

一次典型的"这船怎么配"问答，**应该 0 次 MCP 调用**。

只有三种情况需要调工具：

1. 用户要**针对自己的情况定制**（技能/预算/对手不同）→ `can_fit` / `fit_index` 验证新配装
2. 用户贴了**一套不在库里的配装** → `fit_index` 算它的数值
3. **库里没有这个船型** → `sde_type` + `zkb_search` 现场补

其余一律读文件。

## 一、检索决策树（30 秒版）

```
用户问配船
├─ "某船怎么配"        → README 索引 → vessels/<Group>/<ship>.md → 直接答（0 次 MCP）
├─ "这套行不行"        → 查库同船型 → 对比最接近的配法 → 需要数值才 fit_index（1 次）
├─ "X 和 Y 怎么选"     → 读两个船型文件（多有对比节）→ 0 次
├─ "为什么/原理"       → principles.md / experience.md → 0 次
├─ "某船没收录"        → 明确说"本库未覆盖" → 可选 sde_type（1 次）
└─ "要最新 meta"       → 先给 hotness 基线 → 需要才 zkb_search
```

## 二、按场景的操作步骤

### 场景 1：用户问"某船怎么配"（最高频）

```
1. 读 README.md 的「船型总索引」表 → 确认该船状态（✅ / 🔍 / ⬜）
2. ✅ 或 🔍 → 读 vessels/<Group>/<ship>.md
3. 按文件里的「常见配法一览」**从频次高到低**给
4. 每条配法给：EFT + 为什么有效 + 什么场景 + 什么情况下换成别的
5. 不给"唯一答案"，给场景分支
```

**这一步不要调任何 MCP。** 六维数值、EFT、频次、机制解释，文件里全都有。

例外：用户说"我技能只有 4 级 / 预算 X / 对手是 Y"时，才需要：
- `can_fit(ship, module)` 验证模块能否装（1 次）
- `fit_index(<改后的 EFT>)` 算新数值（1 次）

### 场景 2：用户贴了一套配装问"行不行"

```
1. 判断输入格式：
   - EFT 文本（[Ship, Name] + 模块列表）→ **直接用 fit_index**，不要 fit_parse
   - killmail 链接 → 先 fit_parse 拿 EFT，再 fit_index
2. 查库有没有同船型 → 指出它最接近哪一类配法
3. 说明：属于哪一类 / 偏离在哪 / 预期什么场景
4. 需要约束检查时再 can_fit
```

**不做合规判断。** 本库立场：只解释"这套在什么场景有效"，不判对错。

### 场景 3：X 船和 Y 船怎么选

```
1. 读两个船型文件 → 很多已有「与其他船型的对比」节
2. 没有对比节 → 按这个顺序比：
   加成指向定角色 → 槽位决定能装下什么 → 坦克方式 → 射程/机动 → 典型场景
3. 0 次 MCP
```

### 场景 4：库里没有的船（⬜ 未覆盖）

```
1. 查索引表确认未覆盖
2. **必须明确说"本库未覆盖该船型"** —— 不得凭常识编
3. 可选补充（必须标注"非库内结论"）：
   - sde_type(船名) → 槽位/硬点/船体加成（1 次）
   - zkb_search(ship=..., side=losses, past_seconds=604800) → 近期样本（1 次）
   - fit_parse 抽 1-2 条 → 主流配法（1-2 次）
```

### 场景 5：原理、为什么、某条规则

```
1. principles.md（7 条原则：P-001 ~ P-007）
2. experience.md（16 条经验：E-001 ~ E-016）
3. 0 次 MCP
```

### 场景 6：要最新 meta

**库是 2026-11-03 的快照。** 用户问"现在什么最强"时：
1. 先用 `raw/hotness.json`（T1）/ `raw/hotness-t2.json`（T2）给历史基线
2. 需要最新数据才 `zkb_search(past_seconds=604800, limit=40)`
3. **必须说明"库内数据是 2026-11-03 的快照，以下为实时补充"**

## 三、工具选择速查表

| 你的需求 | 用这个 | 常见误用 |
|---|---|---|
| 库里有这个船型 | **read 文件** | ❌ 调 MCP 重算 |
| 配装能不能装 | `can_fit` | |
| 六维数值 | `fit_index` | ❌ 对已收录配法重算 |
| 拆件归因 | `fit_sensitivity` | |
| 船型结构、船体加成 | `sde_type` | ❌ 凭记忆说槽位数 |
| 名字 → type_id | `sde_search` | |
| 找战损样本 | `zkb_search` | ❌ 自己拼 zkb API |
| **kb → 完整配装** | **`fit_parse`** | ❌ **`fit_killmail` 不含模块清单** |
| kb → 战报上下文 | `fit_killmail` | ❌ 用它找模块 |

## 四、反模式：这些调用是浪费

1. **一上来就 `zkb_search`** —— 库里有 28 个船型的现成分析，先读文件
2. **对库内已有配法重跑 `fit_index`** —— 数值就在文件里
3. **用 `fit_parse` 解析用户直接给的 EFT 文本** —— 已经解析过了，直接 `fit_index`
4. **用 `fit_killmail` 找模块** —— 它只给战报上下文（伤害、参与者、价值），**不含模块清单**
5. **重复查热度** —— 两份 hotness 已落盘
6. **同一配装反复跑不同技能档** —— 除非用户明确说自己技能不到顶，否则用 `all5`
7. **为了"看起来完整"而连调一串工具** —— 回答一个问题通常只需要 **0–2 次**调用

> 判断标准：**每一次工具调用，都应该是为了填补一个"库里有但没有"的空**。

## 五、引用数值时必须带的前提

库里的数值全部标注了前提，引用时**不要丢掉**：

| 前提 | 内容 |
|---|---|
| 技能档 | 默认 `all5`；T2 需注明 all5 还是 all4+min_required |
| 伤害剖面 | **uniform（25/25/25/25）**，真实战况取决于对手。EHP/抗性结论必须带此前提 |
| **T2 突击护卫舰的 EHP** | 含 **ADC 窗口**，虚高约 4 倍（拆掉后降 75%），**不能与 T1 直接比** |
| **`repair_total_hp_s`** | **只算自修**。后勤舰全是 0，不代表它不修 |
| **无人机 DPS** | `fit_index` 按**机库全量**求和，机库超编会虚高 60%+。引用前核 flags |
| **`cap_stable_pct = 100`** | 可能是假稳定。要看 `cap_load_gj_s` 是否为负 + `has_external_dependency` |
| **拦截泡 / 诱导 / ECM** | 工具**不建模**。`fit_sensitivity` 的 `delta = 0` **不代表没用**，代表价值不在六维里 |
| **`fit_sensitivity` 标 additive** | 也可能不闭合，**先验 Σ** 再决定能不能相加 |

## 六、库的目录结构

```
fitting-kb/
├── README.md              ← 总索引 + 方法论。**任何问题都先读这个**
├── principles.md          ← 7 条配船原则（P-001 ~ P-007）
├── experience.md          ← 16 条经验（E-001 ~ E-016）
├── vessels/<Group>/<ship>.md   ← 28 个船型的详细分析
├── raw/<ship>/index.json       ← 该船型的样本与 EFT 证据层
├── raw/hotness.json            ← T1 热度榜（40 船型）
├── raw/hotness-t2.json         ← T2 热度榜（52 船型）
└── _templates/                 ← 模板与术语表
```

**读文件顺序**：`README.md` 索引 → 目标船型文件 → 需要原理时再翻 principles/experience。

**不要**一上来直接 grep 整个目录——索引表已经把所有船型列好了。

## 七、回答风格（库的既定立场）

1. **只做正向归纳**：不判"配得对不对"，只解释"为什么这样配有效、在什么场景用"
2. **频次即推荐度**：频次最高的 = 默认推荐；低频配法照录，不评判
3. **必须给场景分支**：不要给"唯一最佳答案"，给"如果你要 X 就 Y"
4. **库里没有就说没有**：不得用常识填补未覆盖的船型
5. **低热度 ≠ 低价值**：后勤、侦察、拦截这些专用位战损少，**是因为它们活得好**，不是没人用

## 八、术语

用 EVE 中文玩家实际会说的词。完整对照见 `_templates/glossary.md`。几个高频的：

- neut → **毁电**（不是"注电"；注电是 cap booster，给自己供电）
- scram → **短反 / scram**；disruptor → **长反 / point**
- Damage Control → **损控**；PDS → **能诊**
- Trimark Armor Pump → **三角插**
- **抗性一律写百分比**（"爆炸抗性 10%"），不要写"共振 0.9"

## 九、一个完整示例（3 次调用以内）

**用户**："低安单挑，2000 万预算，Rifter 怎么配？"

```
1. read README.md → 索引显示 Rifter ✅，Frigate 组
2. read vessels/Frigate/rifter.md → 4 个配法，频次最高的「甲抗近战 AC+SAAR」2/6
3. 直接答：
   - 主推：甲抗近战（给 EFT，来自文件）
   - 数值：DPS 188 / EHP 3211 / 675m（文件里有，不用算）
   - 为什么：贴脸把三炮 DPS 打进、SAAR 撑开局爆发
   - 预算适配：文件里已有「钢板变体（12.0M）」比 Trimark 变体（28.3M）便宜
   - 场景分支：能控距 → 换配法 3（Arty 风筝）
4. 用户没提技能，默认 all5；如果要低技能适配，才调 can_fit / fit_index
```

**总调用：0 次 MCP，2 次文件读取。**

这就是目标形态——**库的价值在于"不用再算一遍"**。
