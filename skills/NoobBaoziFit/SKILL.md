# EVE 配船知识库 · 使用框架

## 一、先理解这个库是什么，再开始检索

它不是一份"配装清单"，是**从真实战损反推出来的归纳体系**。有四个特征，决定了你该怎么用它：

1. **正向归纳**：只记录"为什么这样配有效、在什么场景用"，**不做配装纠错**。用户问"这套对不对"时，不要下优劣判决。
2. **频次即推荐度**：一个配法在战损里反复出现的次数，就是它的推荐度。**频次最高 = 默认推荐**；低频配法照录、不评判。
3. **它自带不确性与已知风险**：库内明确列了多种数据污染源与工具口径陷阱。**引用任何数值都必须带前提**。
4. **它知道自己覆盖了什么、没覆盖什么**：每艘船有明确状态。

**跳过这些直接找配法，就是跳过了这个库的框架**——你会得到一个数值，但不知道它可不可信、属于哪个场景、该不该推荐。

---

## 二、库的分层，以及为什么不能跳层

| 层 | 回答什么 | 跳过的后果 |
|---|---|---|
| **索引层** | 这艘船有没有？状态如何？热度多少？ | 可能对未覆盖的船硬编答案 |
| **船型层** | 这艘船的常见配法（按频次）、为什么有效、场景边界 | 只知道配了什么，不知道为什么、什么时候该换 |
| **原则层** | 跨船型的可判定规律 | 给不出迁移到新情况的判断 |
| **经验层** | 机制解释与工具口径（窗口件、无人机求和、只算自修…） | 会误读数值，把窗口值当稳态 |
| **证据层** | 原始样本、EFT、热度基线 | 无法回查、无法验证结论 |

**正确顺序永远是：索引 → 船型 →（按需）原则/经验 →（按需）证据。**
反过来（先翻证据层再拼结论）会得到碎片，且容易违反库的判据。

## 三、三条解读纪律（不遵守必然答错）

1. **先看状态，再回答**
   每艘船有状态：已收录 / 草稿 / 未覆盖。
   - **未覆盖 → 必须明确说"本库未覆盖该船型"**；可以给通用分析，但必须标注为非库内结论。**不得凭常识编。**
   - 草稿 → 可答，附一句"该条目待人工确认"。
   - **变体（Fleet Issue / Navy Issue / 势力版）与母船是两条船**：收了 `Hurricane` **不等于**收了 `Hurricane Fleet Issue`（type_id、槽位、硬点、加成全都不同）。库里只有母船时，**变体一律按未覆盖处理**，不得拿母船的配法套上去当库内结论。

2. **按频次给，不按数量给**
   用户问"怎么配"时，从频次最高的配法开始，并给"如果你要 X 场景则换 Y"的分支。
   **不要给唯一最佳答案**——库里几乎所有船都有 2–5 条并行配法，服务于不同场景。

3. **引用数值必须带前提**
   每个数字都挂着前提（技能档、伤害剖面、窗口型件、只算自修…）。
   **丢掉前提的数字等于编造。**

## 四、六种场景：用哪一层、要不要调工具

### 场景 1：用户问"某船怎么配"（最高频）

**索引层确认覆盖 → 船型层按频次给 → 需要解释时引原则/经验层。**

- **不要调工具。** 六维数值、配法频次、机制解释，库内都是现成的。
- 每条配法给三层：**为什么有效 → 什么场景 → 什么情况下换成别的**。
- 只有用户补充了**约束条件**（技能不到顶 / 预算 X / 对手是 Y）时，才需要现场验证。
- **例外：库内没有这台船、配装是现场合成的时候不算"已有的配法"。** 此时按场景 4 声明未覆盖，并且**交付前至少过一次配装解析**——否则手上没有一份规范 EFT 文本，格式与弹药都会被自己写错（§十）。

### 场景 2：用户贴了一套配装问"行不行"

**用船型层做对照 → 指出它最接近库里哪一类 → 说明偏离点与预期场景。**

- 本库**不做合规判断**：回答"这套在什么场景有效"，而不是"这套对不对"。
- 用户给的是裸 EFT 文本 → 它已经是结构化输入，**不需要再解析一次**，直接算数值。
- 用户给的是战损链接 → 需要先取出配装。注意：**战报上下文工具不返回模块清单**，取配装要用能解析配装的那一个。

### 场景 3：X 船和 Y 船怎么选

**两边的船型层都读 → 很多船型卡内已有横向对比节。**

没有对比节时按这个顺序比：**加成指向定角色 → 槽位决定能装下什么 → 坦克方式 → 射程/机动 → 典型场景**。

- **0 次工具。**

### 场景 4：库里没有的船

**索引层确认未覆盖 → 明确说"本库未覆盖" → 可选补充必须标注"非库内结论"。**

现场补充时，每次都要标注来源，并说明"这不是库内结论"。

### 场景 5：原理、为什么、某条规则的来龙去脉

**原则层 + 经验层。0 次工具。**

注意：原则层里每条都带**适用范围与反例**（例如"这条只在 T1 护卫舰成立，战列舰会翻过来"）。**引用时必须连同边界一起给**，否则会被外推成错误结论。

### 场景 6：要"现在什么最强 / 最新 meta"

**本库是 2026-11-03 的快照。**

1. 先用库内**热度基线**回答"历史分布如何"——这是库的强项，且 0 次工具调用
2. 需要最新数据才现场采集
3. **必须说明"库内数据是 2026-11-03 的快照，以下是实时补充"**

**并且提醒：热度 ≠ 强度。** 库内明确记录了热度指标的多种污染源（赶路配、PvE 刷怪、gank 自损、存活偏差）。**热度榜只能粗筛，不能直接当"哪艘船强"。**

## 五、判断标准：这次调用该不该发生？

> **每一次工具调用，都应该用来填补一个"库里有但没有"的空。**

工具分三类，用途不要混：

| 类别 | 用来干什么 | 不要用来 |
|---|---|---|
| **解析配装** | 从链接/文本取出结构化模块清单 | ❌ 拿战报上下文（只有伤害与参与者） |
| **算数值** | 六维（火力/生存/机动/资源/约束/稳定） | ❌ 对库里已有的配法重算 |
| **查事实** | 船型属性、加成、名字↔id、战损样本 | ❌ 凭记忆报槽位与硬点（最容易出错的一项） |

**七条反模式**

1. 一上来就查战损样本 —— 库里已有 28 个船型的分析，先走索引层
2. 对库内已有配法重算数值 —— 数值就在船型层里
3. 解析用户已经贴好的 EFT 文本 —— 它已经是结构化的，直接算
4. 用战报上下文工具找模块清单 —— 它不返回模块
5. 重复查热度 —— 热度基线已落盘
6. 同一配装反复跑不同技能档 —— 除非用户明确说技能不到顶，否则按库内默认档
7. 为了"看起来完整"连调一串工具 —— 一个问题通常只需 **0–2 次**调用

---

## 六、什么时候确实需要现场验证

只有这三种，且每次控制在一两次调用内：

| 触发条件 | 做什么 |
|---|---|
| 用户给了**库里没有的新配装** | 算一次六维，看资源是否可行 |
| 用户说**技能/预算/对手**与库内不同 | 验证关键模块能否装上；必要时算一次新数值 |
| 用户问的船**未覆盖** | 先查结构判断角色，再抽 1–2 条样本看主流配法 |

**一个反直觉的点**：可行性检查里，"能不能飞"取决于**资源余量**，不取决于**违规计数**——库内有实测记录（违规多但可飞 vs 零违规却飞不起来）。不要在"有违规项"上直接下结论。

---

## 七、引用数值时必须带的前提

- **技能档**：默认全 5；T2 需注明是全 5 还是降档
- **伤害剖面**：固定均匀剖面（四系均分 25/25/25/25），**真实战况取决于对手**——任何 EHP / 抗性结论都要带这句
- **窗口型件**：突击损控、辅助修这类是"有窗口、有冷却"的爆发件，而**工具按常开计入**。T2 突击护卫舰的 EHP 因此虚高约 4 倍，**不能与 T1 直接比**
- **维修量只算自修**：后勤舰的修量指标全是 0，**不代表它不修**
- **无人机火力按机库全量求和**：机库超编会虚高 60% 以上，引用前必须核在飞上限
- **电容"稳定 100%"可能是假稳定**：要看负荷是否为负、是否有外部依赖
- **未建模的功能件**：拦截泡、诱导力场、ECM 这类工具不建模，**拆件 delta = 0 不代表没用**，代表它的价值不在六维里

## 八、库的立场（不要违反）

1. **不做配装纠错**：不问"对不对"，只答"为什么有效、什么场景用"
2. **频次即推荐度**：不按"我觉得哪个好"排序
3. **必须给场景分支**：不给唯一答案
4. **未覆盖就说未覆盖**：不得用常识填补
5. **低热度 ≠ 低价值**：后勤、侦察、拦截这些专用位战损少，**是因为它们活得好**，不是没人用

## 九、表达规则：缩写必须展开（硬性，被用户明确批评过）

**给用户的回答里，任何缩写首次出现时必须给出中文全称**，必要时附英文全称。

| ❌ 错误 | ✅ 正确 |
|---|---|
| "两个改装槽都上 CCC II" | "两个改装槽都上**电容控制电路 II（Capacitor Control Circuit II）**" |
| "XL 紧凑盾修" | "**超大型紧凑型护盾回充器（XL Compact Shield Booster）**" |
| "4 个 DDA II" | "4 个**无人机伤害增幅器 II（Drone Damage Amplifier II）**" |
| "中槽放 LSE" | "中槽放**大型护盾扩展装置（Large Shield Extender）**" |
| "上 ADC" | "上**突击损伤控制（Assault Damage Control）**" |

**判断标准**：如果这个缩写需要读者查资料才知道是什么，就必须展开。**拿不准就写全称。**

**唯一例外**：
- 玩家圈内无需解释的通用词：DPS、EHP、CPU、PG、T1、T2
- 同一条回复里已经展开过的缩写，之后可以直接用

**同时不要用 agent 的内部术语**：说"工具调用"，不要提 agent 侧的协议名；说"配装文本"，必要时注明它是什么格式。

**⚠️ 库内文件为了简洁大量使用缩写**（LSE、XLASB、DDA、CCC、OTE、DC…）。**认得出它们是给作者的方便，不是给读者的。** 读到缩写要能对上全称，但**输出给用户时必须展开**——不要把文件里的写法直接倒给用户。

## 十、配装文本的输出格式（硬性）

**交给用户的配装本体必须是严格 EFT，不是"看起来像配装"的摘要。** 装配件一行一件，数量由**重复行**表达。

| 元素 | ✅ 正确 | ❌ 错误 |
|---|---|---|
| 装配件 | 同一行重复 N 次 | `720mm Howitzer Artillery II ×6`（EFT 没有这种语法） |
| 弹药 | `模块, 弹药` 写在**同一行** | `模块, 弹药 ×6` —— 数量会被并进弹药名 |
| 无人机 / 货舱 | `Acolyte II x5`（ASCII `x`，**只有这里**能用数量） | 把 `xN` / `×N` 套到装配件上 |

```text
[Hurricane Fleet Issue, 720mm 舰队散打 MWD]
Damage Control II
Gyrostabilizer II
Gyrostabilizer II
Reactor Control Unit II
Tracking Enhancer II
Tracking Enhancer II

50MN Quad LiF Restrained Microwarpdrive
Large Shield Extender II
Multispectrum Shield Hardener II
Warp Disruptor II

720mm Howitzer Artillery II, Republic Fleet EMP M
720mm Howitzer Artillery II, Republic Fleet EMP M
720mm Howitzer Artillery II, Republic Fleet EMP M
720mm Howitzer Artillery II, Republic Fleet EMP M
720mm Howitzer Artillery II, Republic Fleet EMP M
720mm Howitzer Artillery II, Republic Fleet EMP M

Medium Core Defense Field Extender I
Medium Core Defense Field Extender I
Medium EM Shield Reinforcer II

Acolyte II x5
```

**为什么这条是硬性的**（两条都是实测过的）：
- 写成 `模块, 弹药 ×6`，解析器会把逗号后的**整串**当成弹药名（认成 `Republic Fleet EMP M  ×6`），直接报"认不出这个模块"。
- 更糟的是把六门炮写成重复行、**却把弹药丢掉**：引擎**不报错**，按空炮算——同一套配装 DPS 从 **434 掉到 79**（只剩无人机），静默错 5 倍以上。

**叙述与表格里可以继续用 `6×HAM II`、`3×BCU` 这类缩写**（那是给人读的摘要），但**任何会被贴回游戏或工具的配装块，必须严格按上表**。

## 十一、一个完整示例的形态

**用户**："低安单挑，2000 万预算，Rifter 怎么配？"

- 索引层确认已收录 → 船型层按频次给主推配法
- 数值直接用库内的（**不重算**）
- "为什么"引船型层的机制：贴脸把三炮 DPS 打进、辅助修撑开局爆发
- 预算适配：库内有低价变体，直接给
- 场景分支：能控距 → 换成远距那套
- 用户没提技能 → 用默认档；**只有用户说技能不足时才去验证**

**目标形态：0 次 工具调用、1–2 次读取。**

> 这个库的价值在于"不用再算一遍"——但前提是**先用它的框架**，而不是把它当成一堆等着被 grep 的文件。
